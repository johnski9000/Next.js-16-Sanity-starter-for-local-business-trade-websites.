# SEO Playbook

The single playbook for running SEO on a site built from this template. It covers
the *methodology* — how to read GSC / GA4 / GBP / Ahrefs data and act on it,
content strategy, citations, GBP posts, attribution, the review cadence, and the
hard-won pitfalls. It does **not** repeat setup/install — see the
[README](../../README.md) and [`.env.example`](../../.env.example) for setup and
the env keys.

## Where everything lives

- **Toolkit** — `frontend/seo/*.mjs`, run from the repo root (`node frontend/seo/<script>.mjs`).
- **Client data** — Sanity, read through the GROQ bridge `frontend/seo/_sanity-seo-data.mjs` (`getSettings`, `getAreas`, `getServices`, `getCanonicalNAP`, `getNAPRecord`). There is no hard-coded NAP/cities/services file — Sanity is the source of truth.
- **Paths** — every read/write path and the CSV writer come from `frontend/seo/seo-paths.mjs`, so producers and consumers can never drift.
- **Outputs** — everything lands under `frontend/seo/data/` (gitignored): the Excel workbook, CSV recommendation tables in `data/csv/`, markdown reports, JSON snapshots, and the weekly digest.
- **The only per-client edits to the toolkit itself** are `ahrefs-config.mjs` (`TARGET`, `COMPETITORS`, `PRIORITY_KEYWORDS`, country) and the per-client `AI-HANDOFF.md` (generated by `scripts/onboard-client.mjs`).

## 1. The mental model: three data sources, three questions

The whole programme is about closing one loop. Three sources answer three distinct
questions and must be reasoned about **separately**:

- **GSC — "did our rankings move?"** Impressions / clicks / position, at page and query level, organic only.
- **GA4 — "did the visitors who arrived convert?"** Sessions, key events, conversion rate, at landing-page level.
- **GBP — "did people find the business in the local pack / Maps?"** Location-level only (never per-URL): Search vs Maps appearances, desktop vs mobile, website clicks, calls, direction requests, plus the search terms that surfaced the listing.

A page can rank #4 organically and pull steady GSC clicks while the local pack
above it feeds a competitor every call and direction request — GBP data is the
only way to see that. Read all three together to attribute movement to organic /
local-pack / combined.

**The five levers, in priority order:** (1) striking-distance ranking pushes,
(2) content depth on commercial pages, (3) citations + NAP consistency,
(4) GBP optimisation + posts, (5) earned links (the only lever that meaningfully
moves Domain Rating). When time-constrained, the three highest-value actions are:
pull the 90-day GSC export and run the bucketing analysis; run the Ahrefs scripts
once for a baseline; ship Phase 1 of the #1 striking-distance page. Everything
else can slide a week.

## 2. The weekly cycle (`monday-runner.mjs`)

`node frontend/seo/monday-runner.mjs` runs the whole stack with one command and
writes a single digest. It spawns each step as an independent child process in
order — **a crash/timeout in one step never aborts the run**, and steps share
data only through files on disk, never in-memory, so you must not add cross-step
dependencies (if GSC fails but GA4 doesn't, you still want the GA4 report).

**Order matters** (later steps read what earlier ones wrote): GSC fetch →
phase-2 producers (Sanity content-age snapshot + DataForSEO KD) → GSC analyse
(phase 1 page-level, then phase 2 query-level) → Ahrefs smoke → Ahrefs analyse →
GA4 analyse → GBP analyse → 3-way attribution (last — it reads all upstreams).
Status marks in the digest:
`✓` ok, `⚠` "blocked, not failed" (exit 0 but output matched a quota-gate
pattern — e.g. GBP before allowlist), `✗` failed, `·` skipped/missing. Exit code
is 1 only if a step truly failed (warnings don't trigger cron alerts).

**A run produces** (all under `frontend/seo/data/`): the client Excel workbook
`monday-run-<date>.xlsx`, CSV recommendation tables in `data/csv/`
(page priorities, optimisation targets, keyword gap, position tracker), markdown
reports, JSON snapshots, and the digest `monday-run-<date>.md`.

**How to read it:** read the digest first — scan the step outcomes, then "What to
look at first" in order. The **3-way attribution report is usually the most
decision-shaping output**; if you read one thing, read that. Only then drill into
the underlying reports.

**Discipline:** run Mondays, first thing. ~5–10 min end-to-end (Ahrefs and GSC are
the slow steps). **Don't run mid-week** — the window is 90-day rolling, so a
Wednesday run shifts the window and makes week-over-week comparisons noisy. Skip a
step with `--skip=id1,id2` (valid ids: `gsc-query, sanity-content-snapshot,
dataforseo-kd, gsc-analyse, gsc-analyse-phase2, ahrefs-smoke, ahrefs-analyse,
ga4-analyse, gbp-analyse, attribution, autocomplete-research, xlsx-report`; to save
Ahrefs units use `--skip=ahrefs-smoke,ahrefs-analyse`; to skip the paid KD call use
`--skip=dataforseo-kd`).

## 3. GSC methodology

`gsc-query.mjs` in default (no-arg) mode pulls the standard 90-day page-level
window and writes the canonical export `frontend/seo/data/gsc/gsc-pages-90d.json`.
`analyse-gsc-phase1.mjs` reads it and produces the bucketed report + the
page-priorities CSV.

**Striking distance** — the #1 ROI concept. Canonical definition: **position
11–20 AND ≥100 impressions in 90 days** (the threshold scales with site size).
These pages already rank on page 2 with real demand; small on-page + internal-link
work moves them up fastest. The analyser emits the list automatically (sorted by
impressions) — don't hand-curate it; re-running on fresh data regenerates it. Each
row gets a suggested target of roughly `max(3, pos−5)`. On deploy day, request
manual indexing in GSC URL Inspection for the top ~10 striking-distance URLs
(the quota is ~10/day per property).

**Two movement thresholds, never conflated:** **≥3 places = trend signal** (drives
the Pattern A/B/C direction decision — how many striking-distance pages moved);
**≥5 places = verdict** (per-page Won/Lost scoring). The looser bar is a direction
decision, the stricter bar a quality judgement.

**Bucketing** — the analyser groups every URL by route shape
(`/services/<service>`, `/services/<service>/<area>`, `/areas/<slug>`,
`/projects/<slug>`, `/blog/<slug>`, …) and aggregates impressions/clicks/CTR/median
position per bucket. The impression distribution drives tier decisions (top
sections = focus; absent = candidates to deprioritise).

**The whitelist guardrail** — URLs with >9 impressions in 90 days (≈ >3/month;
raise to 30–100 on high-traffic sites). The whitelist is the guardrail on **every**
destructive op: a currently-ranking page must never be noindexed, pruned or
redirected, **even if its section would otherwise be**. It overrides tier-based
decisions per-URL.

**90-day window discipline** — every pull uses the same window length, dimensions,
and `rowLimit` (25000, the single-call max). The day-zero export is the **frozen
baseline** all later diffs measure against — don't overwrite it. If a pull returns
exactly 25000 rows, GSC is truncating — paginate via `startRow`. You can't compare
a 30-day window to a 90-day baseline.

**Prioritisation cascade** (once the Phase 1 report exists): (1) striking-distance
→ manual indexing today; (2) top-impression URLs → content-depth priority;
(3) bucket distribution → tier classification; (4) zero-visibility URLs minus the
whitelist → noindex + resubmit sitemap for recrawl; (5) whitelist → guardrail on
all of the above.

**Phase 2 — query-level (`analyse-gsc-phase2.mjs`).** Phase 1 is page-level; phase 2
is the keyword-level layer it can't express. It reads three extra GSC exports that
`gsc-query.mjs` now emits (`gsc-queries-90d.json`, `gsc-query-page-90d.json`,
`gsc-query-country-90d.json`) plus the optional KD cache (`dataforseo-kd.mjs`) and
content-age snapshot (`sanity-content-snapshot.mjs`), and writes
`gsc-phase2-report.md` + a query-level striking-distance file. Four checks:
- **① Proven authority ceiling** — the ~90th-percentile KD of queries you ALREADY
  rank top-7 for. That measured bar (not DR/an estimate) is the difficulty new
  keywords should be judged against; with too few proven queries it says so and
  falls back to estimate-based winnability.
- **② Validated quick wins** — query Pos 4-15 + impressions, but each candidate's
  main-market (GB) position is checked against the blended average via the
  query×country export; "phantom rankings" (good blend, poor GB) are filtered out.
  Pages edited <7 days ago are held (cooldown) so GSC can register the last change.
- **③ Re-Eval republish** — Pos 8-25, KD<30, page >6 months old (NavBoost window).
  Recommends a SUBSTANTIVE refresh, never a date-bump.
- **④ Cannibalisation** — one query drawing ≥2 of our pages (common on
  `/services/<svc>/<area>` vs the parent); names the best-positioned target and a
  merge/differentiate call.
Every "add an internal link" recommendation passes a **relevance gate** (a high-click
hub source + topical-match + a descriptive anchor + a one-line user-bridge), so links
flow authority instead of being noise. The KD step is the only paid call (~pennies,
capped); without DataForSEO creds phase 2 still runs and routes on position alone.

**Diagnostics.** Token `400 invalid_grant` = refresh token revoked/expired (most
often the OAuth consent screen left in Testing mode — those tokens die after 7
days). Query `403` = `GSC_SITE_URL` doesn't match the verified property exactly
(URL-prefix needs the trailing slash; domain property is `sc-domain:example.com`
with no protocol — prefer it if both are verified). Empty rows = no data for range
(new properties often return empty for ~2 days). On any review day, test the GSC
pull **early** — an expired token masquerades as "GSC data didn't change".

## 4. Ahrefs methodology

`analyse-ahrefs.mjs` runs the four workflow scripts (gated on an Ahrefs API key);
each calls the named helpers in `ahrefs-query.mjs` — **fix any API-schema drift in
those helpers, never in the workflow scripts.** Outputs land under
`data/ahrefs/{refdomain-snapshots,position-snapshots,keyword-gap,competitor-gap,reports}/`.

**Identify competitors from data, never guess.** Query Ahrefs organic-competitors
first, then filter: drop irrelevant high-DR domains (Wikipedia, Indeed, Reddit,
news); keep 5–7 (too few = weak signal, too many = budget bloat); weight slightly
**above** your DR (aspirational, not far above); validate 1–2 locals by running a
SERP probe on your top head term and picking domains from positions 10–20 in your
geo. Re-evaluate quarterly. Competitor/keyword config in `ahrefs-config.mjs` is the
**only** project-specific edit — re-derive `TARGET`, `COMPETITORS`,
`PRIORITY_KEYWORDS` per client; never reuse another client's lists.

**The four scripts & cadence:** backlink-monitor (weekly; refdomain diff),
position-tracker (weekly; SERP positions for priority keywords), competitor-gap
(monthly; domains linking ≥2 competitors but not you), keyword-gap (monthly;
keywords ≥2 competitors rank top-30 for that you don't). ~8–15k units/month at
default frequency (~10–15% of Lite tier — confirm current limits in the
dashboard). All follow snapshot-then-diff: first run is a baseline; later runs diff
against the prior snapshot.

**keyword-gap → content brief.** The gap table (validated opportunities, sorted by
competitor-count then volume) is the **seed for content briefs** — never write
briefs against guessed keywords. Cross-reference the gap list with the
striking-distance list: where a striking-distance page's topic overlaps a validated
gap keyword, that intersection is the #1 content-brief candidate.

**Schema gotchas worth knowing** (already encoded in the helpers): every
site-explorer endpoint requires a date param or returns 400; the UI "backlinks"
column is `links_to_target` in the API; organic-keywords has no single `position`
field — use `Math.min` over the `all_positions` array; `volume` not
`search_volume`; `order_by` uses a colon (`field:desc`); Lite page-size caps at
100–200 (paginate with offset). The documented env var is `AHREF_API_KEY` (the
wrapper accepts either `AHREF_API_KEY` or `AHREFS_API_KEY`).

## 5. Content depth methodology

Take a thin commercial page (≈1,500–1,900 words) to competitive depth
(≈5,500–6,500 words) against DR 60–70 incumbents. **Phase-gated and deliberately
not collapsed into one PR** — staging lets the 4-week measurement window attribute
movement to a specific change. In this template the editable copy + FAQ arrays live
in Sanity, so "Phase 1 = a content-only change" means **editing the page's Sanity
document fields** (metadata, banner, intro, FAQ array), not touching components.

- **Phase 1** — single-document edits (30 min–3 hr, one PR, no new components). Page moves ≈1,500 → ≈2,800–3,000 words.
- **Phase 2** — new components + body sections (≈6–10 hr), shipped 2–4 weeks **after** Phase 1 and only if the 4-week review shows movement on at least the easiest Tier A keyword. Reaches ≈5,500–6,500 words.
- **Phase 3** — data-gated additions, deferred until the review confirms Phase 1+2 worked.

**KD prioritisation buckets:** KD 0–15 = quick wins (realistic top-20 in 8–12
weeks) → Phase 1 targets, hit explicitly in metadata/H1/intro; KD 16–35 =
medium-term → Phase 2 section additions; KD 35+ = long game, only attempt if your
DR is within ±10 of the lowest-DR top-10 incumbent, else defer. Every brief needs a
"Tier A keywords" table (keyword / volume / KD / which competitors rank top-10);
filter out branded, wrong-vertical, and pure-informational queries first.

**Vocabulary-coverage analysis** — the most underused lens. Even a 3,000-word page
misses wins because the author chose one phrasing and never used alternates. For
each Tier A keyword, check whether the Sanity content contains that exact phrasing
or a close variant. Common gaps: acronym vs spelled-out (PPC vs "pay-per-click"),
old vs new brand ("AdWords" → Google Ads, "Twitter" → X), UK vs US spelling
(optimisation/optimization — prefer GB, include the US variant once), synonym
families (consultant/agency/specialist), long-tail intent ("best X company", "X
near me"). The fix is one natural sentence acknowledging the synonym. A
"vocabulary-coverage rescue" brief can be Phase 1 on its own when depth is already
adequate.

**Competitor word-count benchmark** — for 3–5 top-ranking competitor pages on your
head term, count body words. Typical DR 60–70 service hub: 3,500–6,000 words. At
DR 40–50, at least match the lower bound — the DR gap closes via links over months,
but the content gap closes in one PR.

**Phase 1 checklist** (all in Sanity fields, single PR, ≈800–1,000 new words):
(1) metadata title leads with the lowest-KD commercial Tier A keyword, brand last,
≤60 chars; (2) meta description 150–160 chars with 2–3 Tier A keywords;
(3) keywords array adds every Tier A/B keyword; (4) banner H1 rewritten to the
highest-priority Tier A keyword (one of the strongest single signals);
(5) banner description ≈120 → ≈200 words weaving 6–9 keywords + any vocabulary gap;
(6) intro title + subtitle carry the second keyword; (7) intro body light keyword
sprinkle + internal links to sub-service pages on natural mentions (no new
paragraphs — that's Phase 2); (8) append 6–8 FAQs.

**The 6–8 FAQ template** — each 80–130 words; keyword-targeted question, genuinely
useful answer (generic marketing copy triggers a Helpful-Content demotion). Pick
from: Price, Comparison (agency vs freelancer), Adjacent-vertical, Geographic,
Methodology/trust (E-E-A-T), Anti-pattern (saying "no" builds trust),
Vocabulary-coverage, Adjacent-channel (e.g. "X vs Y"). FAQs flow into FAQPage
JSON-LD automatically.

**Phase 2 sections** (≈2,700 words + 2–3 components): services breakdown (each
service line an 80–150 word **in-page** paragraph — Google doesn't fully credit
linked sub-pages back to the hub); pricing tiers (matches "how much does X cost"
intent, discriminates from competitors who hide pricing); methodology expansion
(4 steps → 8); in-page case studies (only with **real** results — fabricated
triggers a Helpful-Content demotion).

**Phase 3 candidates** (only if the 4-week review is Pattern A): "X vs adjacent
service" comparisons, "X vs in-house", industry-specific landing sections, glossary
(each term ranks for long-tail), video walkthrough.

**Risks to call out in every brief:** cannibalisation (keep hub paragraphs 80–150
words so the hub doesn't compete with its sub-pages); over-optimisation (target
keyword 3–5× in body + once in H1 + once in H2, synonyms carry the rest); Helpful
Content (templated AI copy gets demoted); doorway-page risk (don't paste the same
brief across many pages).

## 6. GA4: conversion attribution

`ga4-analyse.mjs` pulls a 90-day window, saves a dated snapshot, and writes a
baseline (first run) or delta report. The most actionable section is **"high
sessions / zero conversions"** — pages where SEO works but the page fails to
convert; audit those before chasing more rankings.

**GSC × GA4 attribution** (`gsc-ga4-attribution.mjs`) joins the GSC page export
with GA4 landing-page sessions + key events on a normalised pathname, and produces
a **six-section report — each section maps to a different intervention, so don't mix
them up:**

| Section | What it is | Action |
|---|---|---|
| Top pages | Landing pages by clicks, with sessions/conv-rate | context |
| Striking-distance + **high** conv rate | ranks ~page-1-bottom, converts well | **urgent SEO push — highest ROI** |
| Striking-distance + **low** conv rate | ranks but converts poorly | SEO push *and* CRO |
| SEO without commerce | high impressions, ~0 conversions | **CRO problem, not SEO — do NOT add content** |
| Commerce without SEO | converts but low impressions | SEO investment: deepen content, build links |
| Top conversion drivers | pages producing the most leads | defensive: preserve, never touch carelessly |

**The hard rule:** when a page is high-impression / zero-conversion, resist adding
content — it already has visibility; audit CTA, form, page-speed, and intent match.
If the query is informational but the page is transactional, fix it with a **new**
informational page that internally links to the transactional one — don't bolt
commercial copy onto a research page.

**Thresholds** are tuned for a low-volume local site (striking-distance = pos 5–25
with ≥50 impressions; SEO-without-commerce = ≥200 impressions and 0 conversions).
On a property doing >10k clicks/month, raise them all or the tables become
unreadable.

**Gotchas:** GA4's conversion metric was renamed `conversions` → `keyEvents` in
mid-2025 (requesting the old name returns a hard 400 — the wrapper pins `keyEvents`
and auto-probes `/metadata`; don't "fix" it back). `GA4_PROPERTY_ID` is the numeric
property id, **not** the `G-XXXX` Measurement ID. An empty GA4 report usually means
the gtag isn't firing in production, not a bug — check for `collect?v=2` requests in
devtools.

## 7. Google Business Profile (GBP)

**GBP is optional.** Leave `GBP_ACCOUNT_ID` / `GBP_LOCATION_ID` unset and the Monday
runner skips the GBP step cleanly (`· skipped (not configured)`) and the 3-way
attribution falls back to GSC×GA4 — nothing breaks. Enable it when you want
local-pack data (the highest-value channel for most local trades).

**The quota allowlist gate is the single biggest GBP blocker.** Google sets the
Business Profile **Performance** API quota to **zero** on new Cloud projects — every
Performance call returns 403 `RESOURCE_EXHAUSTED` (quota_limit_value=0) until you
submit the access form at `support.google.com/business/contact/api_default`. Submit
it **immediately** after enabling the APIs (don't wait); approval takes ~7–10
business days; save the case ID in `AI-HANDOFF.md`. On the form choose "manage my
own business" (the agency/"on behalf of clients" tier is a slower, stricter queue).
Build the scripts now anyway — they detect the 403, print a banner, and exit 0, so
they no-op cleanly until approval lands. (Account Management + Business Information
APIs are *not* quota-gated — a healthy pre-approval state is accounts OK, locations
OK, performance FAIL.)

Enable **three** APIs on the OAuth client's project: My Business Account Management,
My Business Business Information, and Business Profile Performance (not the
deprecated v4 "Google My Business API"). The single scope
`https://www.googleapis.com/auth/business.manage` covers all of it. Run
`gbp-discover.mjs` once after `.env` is set to enumerate accounts/locations and
confirm each API; `GBP_ACCOUNT_ID`/`GBP_LOCATION_ID` come from the
`business.google.com/n/{account}/profile?fid={location}` URL.

`gbp-analyse.mjs` runs weekly: 90-day totals, Search-vs-Maps and
Mobile-vs-Desktop splits, top 30 search keywords, and daily sparklines; it flags
any headline metric down ≥20% and any single keyword driving >30% of impressions.
(Low-volume keywords come back as `{threshold:'5'}` meaning <5 impressions — render
as "< 5", don't strip them; they're the longest tail.)

**Service-area decision tree (SAB vs non-SAB):** Google treats any business that
hides its address as a service-area business. (1) **Pure SAB** (trades): 90-minute
drive radius, 8–15 areas, address hidden. (2) **Remote-delivery**: catchment driven
by demand not drive time; **12–16 areas is the sweet spot** (Google supports 20;
17+ dilutes the signal) — these should match your tier-1 area pages. (3)
**Brick-and-mortar with footfall**: address **shown** (non-SAB), service area =
primary city + 3–5 sub-areas (don't claim distant cities — Google penalises
non-SAB businesses that do). Decision flow: customers come to you → Pattern 3;
otherwise remote → Pattern 2, you travel → Pattern 1.

**Curation & replication rules:** curate ~30 GBP services (it supports 60, but
loading all dilutes relevance — start from your service list, filter to Ahrefs
volume >200/mo or top GSC impressions). The **most-violated rule:** list all
service areas **only** on GBP + Bing Places + Apple Business Connect (the three
that support service-area mode); every other citation gets **one** primary address —
listing multiple areas on a single-address directory makes the NAP fingerprint
noisy.

**GBP listing audit** — a 13-section monthly self-audit (NAP, categories, service
area, services/products, description, photos, posts, reviews, Q&A, attributes,
hours, links, verification), each writing back to the citations tracker. Template
cross-check: every GBP service-area city **must** resolve to a published, indexed
area page on the site (an area in the GBP picker with no live `/areas/<slug>` page
feeds a 404 and inverts the trust signal). NAP must match the canonical source
byte-for-byte; concrete field mappings — GBP service descriptions from
`service.summary` (≤220 chars), the 750-char GBP business description from
`settings.seo.description`, hours from
`settings.structuredData.localBusiness.openingHours[]`. Google silently trims SAB
listings over ~20 areas — force a save-and-reload to detect it.

**3-way attribution** (`gsc-ga4-gbp-attribution.mjs`) extends the GSC×GA4 join with
a GBP overlay: location-level GBP totals + top GBP keywords side-by-side with GSC
queries, plus a per-URL "GBP-attributed sessions" column derived from GA4
source/medium (regex `/(maps|business|gmb)/i`). **State plainly that this per-URL
column is a proxy**, not exact Performance-API data. It degrades gracefully — if GBP
quota isn't granted, GA4 has no traffic, or `gbp-query.mjs` is absent, it still
writes both output files with a banner.

## 8. GBP posts

**The post-creation API is dead for SMBs** (Google deprecated `localPosts` in April
2024; `business.manage` does not grant programmatic post creation). Posts are
**authored in markdown and pasted manually** via `business.google.com` → Posts.
Don't wire direct API publishing — it 403/404s.

**Hard constraints** (the verifier treats each as a hard fail): body ≤1,500 chars;
opening line ≤80 chars (≤58 ideal — it's the preview before "Read more"); no raw
URLs in the body (GBP strips them); no clickable inline links (only the CTA button);
no emojis (B2B); no markdown (renders literally); brand name exactly once,
mid-post; target keyword 1–3× with the first in the opening line; CTA closer names
the exact button text; image 1200×900 (4:3), ≤5MB. The CTA button is a closed set:
Book / Order online / Buy / Learn more / Sign up / Call now (anything else → post
type "Update" with no button).

**Cadence & mix:** monthly batches of 8 posts (2/week × 4 weeks), default mix
**3 Local / 2 Sector / 2 Striking-distance / 1 Free-tool** (calibrate to inventory).
Monday posts skew educational/local; Thursday posts skew offer/conversion. GBP posts
persist ~6 months but the local-pack signal weights recency hard — a stale profile
loses visibility within ~2 weeks. After ~2 weeks of Insights data, shift the next
batch's mix toward what performed.

**5-phase authoring workflow** (don't collapse — each phase gates the next; phases
3–4 parallelise across 8 sub-agents): **(1) Discover** — read the
striking-distance report, Ahrefs quick-wins, areas/services/recent-projects from
Sanity, brand voice, canonical NAP, and **previous batches** in
`frontend/seo/gbp-posts/` (to avoid repeating target URLs/keywords within 90 days).
**(2) Strategy** — an 8-row calendar (slot, week, day, angle, post_type,
target_keyword, target_url, cta_button, rationale) **before** any body copy; angle
distribution must equal 3/2/2/1, no duplicate target_url/keyword vs prior batches.
**(3) Author ×8** — one sub-agent per slot. **(4) Verify ×8** — an adversarial
verifier per post checks every constraint and **fixes inline** (doesn't bounce
back). **(5) Assemble** — stitch into `frontend/seo/gbp-posts/YYYY-month-N-8-posts.md`
with each post body inside a triple-backtick fence (non-negotiable — without the
fence, paragraphs collapse on paste).

The **"what we did this week in <area>"** post type is high-value: discovery pulls
recent projects from Sanity (`*[_type=='project' && defined(completedAt)] | order(completedAt desc)`),
links the post to the project page, and attaches its cover image. Schedule
typed-area posts before fringe/extra-coverage cities.

## 9. Citations & NAP

**Canonical NAP discipline is the single highest-leverage citation work:**
byte-identical NAP everywhere. Inconsistency ("Rd" vs "Road", "+44 161" vs "0161",
trailing spaces) actively hurts ranking — Google can't entity-match the listings.
**The one source of truth is Sanity `settings.structuredData.organization`;**
everything else — footer, mobile sticky CTA, JSON-LD ContactPoint, the citations
README block, the CSVs — is a **derived artifact**. Never hard-code a NAP constant
in a toolkit script. Regenerate the derived block/CSVs after every NAP edit, and
make `sameAs[]` mirror the footer social links (flag drift during audit).

**Three tracking CSVs** (Google-Sheets import format; written under
`frontend/seo/data/csv/` via the `writeCsv` helper; templates live in
`frontend/seo/citations/`): `business-info.csv` (Section/Field/Value, with **six**
description lengths because directories cap differently — 50-char, ~180-char,
~50-word, ~150-word, ~300-word, 1500-char — write all six once so it's copy-paste);
`services.csv` (Category / Service / Slug / SEO Description / Keywords, one leaf per
row from the Sanity services); `citations-tracker.csv` (13 columns; status
vocabulary Not Started / In Progress / Submitted / Verified / Live / Skip — keep
skipped rows with a Notes rationale, never delete them).

**The 6-tier framework** (work top-down by trust-leverage-per-hour):
- **Tier 1 — universal core** (all live by end of week 1): Google Business Profile (SAB mode), Bing Places ("Import from GBP"), Apple Business Connect, a national directory (Yell in the UK), Foursquare, Trustpilot, Yelp.
- **Tier 2 — national directories + B2B credibility**: the national company registry (Companies House — verify the office address matches NAP), national free directories (FreeIndex/Hotfrog/Cylex/192.com), Crunchbase, LinkedIn Company Page.
- **Tier 3 — regional** (must be **re-sourced per catchment** — never reuse another client's list): the local council business directory, regional newspaper directory, local Chamber of Commerce, sector cluster orgs.
- **Tier 4 — sector-specific**: the trade body or sector lead/review platform relevant to the client (e.g. Gas Safe, NICEIC, FMB, Checkatrade for trades; Clutch + verified reviews for B2B agencies). A/B test paid lead platforms before spend.
- **Tier 5 — social + lead aggregators** (mostly audit-not-create for established businesses).
- **Tier 6 — earned links** (separate workflow, §11): pitch-driven, the main lever that moves DR.

**SKIP list** — mass-submission services (BrightLocal etc.), generic "free business
directory" aggregators, pay-for-inclusion "top 10" listicles, Upwork/Fiverr. Modern
Google rewards fewer, higher-authority listings, not volume.

**Citation photos** — source from project images (`project.coverImage` +
`project.gallery[]`) via the Sanity CDN, ordered by `completedAt` desc.

**Review acquisition** (citations get you found; reviews convert): per project, on
handover email the client direct review links; +3 days soft follow-up; +7 days a
personal note. Rotate clients across platforms week to week (avoid the "100 GBP / 0
elsewhere" pattern algorithms downweight). **Only pursue genuinely earned reviews —
never fabricate ratings.**

**Refresh cadence:** monthly — audit Tier 1 NAP consistency; quarterly — full NAP
audit (search the business name, verify the top results); annually — prune dormant
listings; after any service-area expansion — update GBP areas and the relevant
Tier 3 citations.

## 10. Coverage & URL inventory (template specifics)

**Two coverage tiers, reasoned about differently:** (1) **typed `area` docs**
(`getAreas()`) are indexable pages at `/areas/<slug>` — the targets for
page-improvement briefs and the high-priority deep-link targets for GBP posts;
(2) **extra-coverage cities** (`settings.structuredData.areaServedCities[]`, via
`getCoverageCities()`) render as plain text on `/areas`, carry lat/long, and are
part of the LocalBusiness `areaServed` graph, but are **not** brief or page targets.
**Union** both lists when reasoning about total coverage; use **only** typed docs
when prioritising work. Never hard-code a city count — derive it live.

**The serviceArea combo-URL publish gate:** `/services/<service>/<area>` URLs are
**gated** — a `serviceArea` doc only goes live when all three hold: `localIntro`
≥120 chars, ≥2 matching projects, and ≥1 testimonial **or** ≥1 FAQ. Until then the
URL 301s to `/services/<service>`. **Critical toolkit rule:** any script emitting an
"expected URL inventory" must reflect only the *published* serviceArea docs — never
the full services × areas cross-product. When a brief or GSC recommendation points
at a combo URL that's currently 301ing, the action is to **complete the
serviceArea doc** to satisfy the gate, not to edit a component.

## 11. Review cadence (the operating rhythm)

Hardcode three review gates on the calendar **before** writing any content:
**Day 0** = freeze baseline snapshots + deploy; **Day 28** = first-signal review →
Pattern A/B/C; **Day 56** = second review + tooling decisions; **Day 84** =
whole-programme decision gate. A review takes 90–120 min — if longer, you're
re-debating settled strategy; stop and execute. Between checkpoints you **execute,
don't re-debate.**

**Three tripwires (10-min risk checks, run FIRST at every checkpoint, before
per-page scoring).** If any fires, stop content work and investigate: (1)
**Main-site impressions stability** — did untouched URLs (home, /services, /about,
/blog) stay stable or grow? A >10% WoW drop means the new work is dragging the
domain — this matters *more* than cluster wins. (2) **Indexed-page count direction**
(GSC Coverage) — up = good, flat = recrawl pending, down by >50 = alarming.
(3) **Noindex effectiveness** — did any URL you noindexed this cycle still
click/rank? It shouldn't; if it did, the noindex didn't propagate.

**Per-page scoring** (for each deepened page): **Won** = position improved ≥5
places; **Stable** = changed <5 (likely too early); **Lost** = dropped ≥5
(investigate); **Crawl-pending** = position unchanged because Google hasn't
recrawled — check Last Crawled in URL Inspection; if it predates your deploy,
request indexing and defer to the next review. Crawl-pending is non-negotiable: it
separates "didn't work" from "hasn't been tested yet".

**Pattern A/B/C** (count striking-distance movers at the ≥3-place trend threshold,
then execute the pre-written action list):
- **A — working** (≥4 of ~7 moved): start Phase 2 of the top mover, round-2 content on top pages, a Tier-4 citations batch, continue review acquisition, more press pitches.
- **B — partial** (1–3 moved, the **most common** at week 4): diagnose non-movers individually (Last Crawled, mobile render, schema), hold round-2 until week 8, invest in 2 earned links rather than more citations, apply winners' pattern to a small test.
- **C — not working** (0 moved): stop content, audit technical SEO of the deepest page + site-wide GSC signals, pivot entirely to link-building (DR is likely the gate), re-evaluate at week 8.

Resist declaring victory on A or defeat on C until week 8 confirms.

**KPI tracker** — one weekly table, same row order/labels/units every week (drift
breaks comparability): Domain Rating, referring domains, GBP reviews, Trustpilot
reviews, citations live, cluster/service-page impressions & clicks (90d), top-10
URLs, target-keyword rankings, earned-link wins. Set target **ranges**, not single
targets. Derive every baseline from your own Phase 1 report.

**Weekly maintenance** (~90 min floor): Monday — run the toolkit, check GBP
messages/reviews; mid-week — email 1–2 past clients for a review (rotating
platforms); Friday — one citation submission **or** one press pitch (alternating),
then update the KPI row. If a week has only 90 minutes, the script run is the only
irrecoverable step (it loses WoW comparability).

**Week-8 cancel-or-keep tool protocol** (run once, for Ahrefs): count reports
written weeks 1–8 (<12 → you weren't using it → cancel); did you use the web UI ≥4×
(yes → keep); else trial an alternative (e.g. DataForSEO) on one backlink run and
keep only if it's within ±15% on refdomain count and covers the high-DR ones. Write
the decision + reasoning into the decisions register.

**Decisions register** — keep a dated "decisions made today (don't re-debate)" log
(chosen competitors, the locked striking-distance definition, the GBP service-area
list, Pattern verdicts). Future sessions read it first, which prevents re-litigating
settled scope.

## 12. Realistic targets & honest limits

Realistic (not guaranteed) shapes over 8–12 weeks: **+20–30% cluster impressions**
(Google's recrawl cadence is the bottleneck — un-recrawled pages are "Crawl-pending",
not "Lost"); **clicks 2–3× off a small base** (the absolute count stays small — make
sure the client understands); **5–15 new top-30 rankings** if the keyword-gap
surfaces low-KD opportunities (far fewer if it surfaces KD 50+); **30–40 live
citations** at ~30–60 min/week; **DR +1–3** only if earned-link work is happening.

What the playbook will **not** do: unlock rankings gated by link authority (KD 50+
against a low-DR site needs sustained link-building, not content depth); accelerate
Google's recrawl; write the content for you (the brief is structure + vocabulary
checklist + FAQ targets — prose is craft); fix technical regressions (Pattern C
says stop content and audit technical first); or produce citations that don't exist
in thin industries/regions.

## 13. Branches — when the standard flow doesn't apply

- **Brand-new / <90 days of GSC data** (baseline pull returns <10 rows): skip the bucketing analysis; still set up GSC + Ahrefs (Ahrefs has competitor data even when your domain has none); spend weeks 1–4 on technical baseline + 5 cornerstone pages + GBP/Tier-1 citations; at ~90 days run the full Phase 1 analysis and rejoin the standard cadence.
- **Business shape:** e-commerce → skip GBP/citations, bucket by `/collections//products//pages//blogs/`, raise the whitelist threshold to 50–100; SaaS marketing site → skip citations entirely, use GSC + Ahrefs + content depth; brick-and-mortar → GBP shows the address (non-SAB).
- **Non-UK markets** → re-source Tier 3 entirely and substitute Tier 1/2/4/5 platforms (US: BBB, Yellow Pages; DE: Gelbe Seiten; FR: Pages Jaunes); replace currency/VAT/regulator references.
- **Commercial-tier vs geo-tier** (multi-location sites): separate a city's geographic size from its commercial SEO demand — a small affluent town can be commercial-tier 1. Drive noindex from commercial-tier + the impression whitelist, never geo-tier, and always with a per-URL whitelist override. In this template "tier" is a Sanity field, not a code registry.

## 14. Agency operating model

- **Multi-tenancy:** one-repo-per-client for ~5–20 clients (clean isolation, per-client `.env` + Vercel project; propagate toolkit upgrades by copying `frontend/seo/*.mjs` into each repo). Only consider a true multi-tenant architecture at ~50+ clients.
- **Credential split.** Agency-shared: `GOOGLE_CLIENT_ID/SECRET` (one Cloud project + OAuth app; add each client deploy URL to the redirect allowlist), the **GBP quota allowlist** (per Cloud *project*, so one approval covers all clients), the Ahrefs key. Per-client (must differ): Sanity project/dataset/write token, `NEXT_PUBLIC_SITE_URL`, `GSC_SITE_URL`, `GA4_PROPERTY_ID`, `GBP_ACCOUNT_ID/LOCATION_ID`, SMTP/contact email. `GOOGLE_REFRESH_TOKEN` can be shared **only if** the agency Google account has access to every client's GSC/GA4/GBP (verify after onboarding).
- **OAuth one-shot scopes:** Google issues one refresh token per authorisation carrying only the scopes granted at consent time — you can't add scopes to a long-lived token later. Grant the full set in a single OAuth Playground exchange (`webmasters.readonly` + sitemap write, `analytics.readonly` + `analytics.edit`, `business.manage`, `indexing`). When you re-grant, the new token **replaces** the old — update `GOOGLE_REFRESH_TOKEN` immediately and re-run the GSC smoke test.
- **Token boundary:** the toolkit needs **read** access only — never give it (or production) the Sanity write token, so a compromised audit run can't mutate the dataset.
- **Offboarding:** revoke the agency Google account from GSC/GA4/GBP (the shared token starts returning 403 within minutes — confirms revocation); transfer Sanity project ownership; transfer/pause the Vercel project; archive the repo; capture a final GSC + ranking snapshot.

## 15. Pitfalls catalog

Append every lesson that costs ≥30 min or invalidates an "obvious" assumption, as
**What happened / Why it matters / The rule** (the rule is the load-bearing line):

- **NAP consistency invariant.** On-site JSON-LD NAP that drifts from live citations degrades local rankings silently (no error, surfaces only as ranking drift). *Rule:* Sanity `settings.structuredData.organization` ↔ on-site LocalBusiness JSON-LD ↔ `citations/business-info.csv` ↔ `citations-tracker.csv` ↔ the canonical README must all match byte-for-byte. One human-edited source, propagated in a single commit.
- **Pin date windows.** Helpers have inconsistent default windows; relying on a default lets a refactor silently shift the window and break WoW comparisons. *Rule:* pin the reporting window explicitly above the first API call and pass it to every helper.
- **Agent workflows leave scratch files.** Verifier sub-agents wrote temp files that polluted `git status` and risked stale re-runs. *Rule:* the orchestrator deletes what it created, or a final agent git-statuses and cleans up; add `.gitignore` patterns for predictable scratch names.
- **Windows build-path casing** (Next.js + Windows only). Building from an uppercased path vs the canonical-cased path triggers a Next async-store invariant during static export, and the error never mentions casing. *Rule:* always launch builds from the canonical-cased path.
- **GBP Posts API is dead for SMBs** (April 2024) — manual paste only.
- **GA4 `conversions` → `keyEvents`** (mid-2025) — old name returns a hard 400.
- **GBP Performance quota defaults to zero** on new Cloud projects — submit the allowlist form first.
- **Per-script `.env` loaders kept inline comments.** Every `frontend/seo/*.mjs` script grew its own `KEY=(.*)` loader that stripped surrounding quotes but not a trailing ` # comment`, so a value filled straight from `.env.example` (which carries an inline comment on every line) such as `DATAFORSEO_PASSWORD="xxxx" # ...` parsed to the literal `xxxx" # ...`. *Why it matters:* every authenticated step (DataForSEO, GSC, GA4, GBP, Ahrefs) silently failed auth (DataForSEO returned 40100) while the creds looked correctly set. *Rule:* strip the inline comment before the quotes, reusing the canonical `parseEnvValue` from `scripts/lib/load-env.mjs`. Never hand-roll a `.env` parser.

A stale pitfalls section is worse than none (it implies a completeness it doesn't
have). API-state notes above reflect Google's APIs as of ~2026 — re-verify if
reading >12 months later.

## 16. Keeping the handoff current

Each client carries a `frontend/seo/AI-HANDOFF.md` (generated by
`scripts/onboard-client.mjs`) so a fresh AI session doesn't burn time rediscovering
paths, status, and pitfalls — **a stale handoff is worse than none, because the AI
will trust it.**

**The keep-current rule:** update the handoff **in the same commit** as any
substantive change — never as an "I'll update it later" follow-up (you forget; it
drifts within weeks). Always update when: active state changed, the toolkit changed
(new script / new env key), NAP/business info changed, you hit a new pitfall, the
strategic priority shifted, or paths moved. Skip for: single content commits,
ephemeral state, failed experiments. The test (fails open — when unsure, update):
*would a fresh AI session miss this if you didn't update?* Bump the `Last updated`
date every time.

**The README cycle prompt** lets the user resume the cadence in a fresh
conversation. Its shape: load `AI-HANDOFF.md` first → run
`node frontend/seo/monday-runner.mjs` → read the latest reports (especially the
3-way attribution) → surface failures first, then the **top 3** findings, then a
**single** recommended next move with reasoning (not a menu) → if anything material
shipped, update the handoff in the same commit. Operator voice: **concise,
decisive, real numbers, no menus.**
